# Adoption guide for Wasl agents

1. Read AGENTS.md, applicable version-control/design/frontend instructions and existing project guidance. Establish clean status and create the worktree/branch as instructed; preserve uncommitted changes.
2. Inventory existing theme/token files, Tailwind version and configuration, shadcn `components.json`, component source and exports, existing HTML design kit, supported variants/states, page patterns, languages and light/dark modes. Record each component, path, variants, usage, dependencies and status.
3. Create a mapping matrix: existing component/variant -> proposed updated equivalent -> visual changes -> behavior/API preserved -> review/test. Every existing item must be accounted for; adapt it even if the new kit has no matching example. Never delete or replace an old component solely because it is absent from this package. Escalate true conflicts with evidence.
4. Compare supplied Gumroad screenshots and reference preview. Use the selected palette and document purposeful deviations. Preview design-library changes first, with genuine event/community card anatomy and representative pages. Leave actual page layout and product behavior unchanged during the design-library review stage.
5. Merge candidate CSS variables into the project's existing theme, preserving existing names and mappings as necessary. `tailwind-v4.css` is an example for v4, not an automatic drop-in for v3. The v3 adapter uses `var(--primary)` as a complete color; adapt to the project's existing HSL/OKLCH channel convention rather than wrapping a full hex value in `hsl()`. Preserve existing dark-mode tokens; don't invent final dark mode.
6. Update existing shadcn components rather than overwriting project implementations or resetting `components.json`. Map actual variants, compositions, spacing and focus behavior; keep API and tests. Preserve all old components and interaction flows.
7. Validate by browser at desktop/mobile and LTR/RTL, keyboard and screen reader spot checks, contrast of all intended token pairs, current app test/lint/build commands and relevant component states. Check image failures and long labels. Report evidence and gaps accurately. Run actual visual review before describing preview as verified.
8. Hand off the preview, mapping matrix, modified files and checks. Seek the user's design review before applying system changes broadly to app pages; follow established branch and cleanup policies.

Suggested matrix headings: Existing component | Source path | Variants/states | Adopted equivalent | Behavior preserved | Gap or decision | Validation.
